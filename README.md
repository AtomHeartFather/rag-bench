# Когда нужен RAG, а когда достаточно поиска по словам? — бенчмарк на домашней машине

Сравнение трёх способов «памяти» базы знаний на одинаковых данных и одинаковых запросах:

| Вариант | Что это |
|---|---|
| **file** | Документы в файлах + BM25-поиск в памяти (прокси «агент сам grep'ит по файлам») |
| **fts** | SQLite FTS5 — классический поиск по словам, без ML |
| **rag** | Qdrant + bge-m3 (1024-dim эмбеддинги) — векторный поиск по смыслу |

Весь стенд: один корпус, одинаковое чанкование (~1500 символов), один набор запросов с gold-ответами.
Метрики на retrieval-этапе (без LLM): **Hit@10** (нашёл ли нужный документ в топ-10), **MRR@10** (где именно в ранге), задержка p50/p95/p99, пик RAM, время и цена индексации.

## Главный вывод — правило выбора

> **RAG нужен, когда данных много (от ~10 тыс. чанков) ИЛИ когда люди задают вопросы «своими словами» — без точных слов из документов. Иначе — обычный поиск по словам: он так же точен, в 10 раз быстрее и ничего не стоит. Голые файлы живут до ~10 тыс. чанков, потом умирают по задержке и памяти.**

Обоснование — в цифрах ниже.

## Результаты на реальных датасетах

Три открытых датасета с gold-документами (MultiHop-RAG, RGB, HotpotQA fullwiki),
от 5k до 66k чанков, 1800 запросов (300/500/1000):

| Корпус (размер) | запросов | Hit@10: file / fts / rag | MRR@10: file / fts / rag | p95: file / fts / rag |
|---|---|---|---|---|
| real-mh (5k, multi-hop) | 300 | 85.7% / 65.3% / 83.7% | 0.55 / 0.38 / 0.50 | 46мс / 1.7мс / 25мс |
| real-rag-10k (11k) | 500 | 88.2% / 90.4% / **96.6%** | 0.60 / 0.64 / **0.78** | 31мс / 2.7мс / 13.7мс |
| real-rag-66k (66k) | 1000 | 94.1% / 96.8% / **98.9%** | 0.73 / 0.80 / **0.93** | **642мс** / 13.6мс / **17мс** |

![accuracy by scale](images/accuracy_by_scale.png)

![latency p95](images/latency_p95_by_scale.png)

Ключевые наблюдения:

1. **RAG ведёт по точности на всех трёх реальных датасетах**, и разрыв растёт с размером
   (на 66k: +4.8 п.п. к поиску по словам). На сложных запросах (L4 comparison в HotpotQA)
   RAG — 100% против 97%.
2. **Поиск по словам проваливается на «живых» вопросах без точных ключевых слов**:
   в real-mh (длинные вопросы-пересказы) FTS5 — 65.3% против 83.7% у RAG. OR-склейка
   ключевиков не ранжирует.
3. **Файлы умирают на объёме**: на 66k чанков p95 поиска — 642 мс (полный перебор корпуса
   на каждый запрос), пик RAM — 2.5 ГБ. На 5k ещё конкурентен, но уже держит весь корпус в памяти.
4. **Цена RAG на домашнем компе приемлемая**: индексация 66k чанков — 24 минуты (одноразово),
   пик RAM Qdrant — 330 МБ, сам поиск — 17 мс p95.

## Синтетика: почему «поисковик» сначала выигрывал

Сгенерированный локальной LLM корпус (1k/10k чанков, 300 запросов, 5 уровней сложности):

| Шкала | Hit@10: file / fts / rag | MRR@10: file / fts / rag | p95: file / fts / rag |
|---|---|---|---|
| 1k (500) | 90.7% / **98.0%** / 96.7% | 0.77 / 0.78 / **0.91** | 0.6мс / 0.4мс / 454мс* |
| 10k (5k) | 89.0% / **98.0%** / 97.3% | 0.73 / 0.71 / **0.89** | 3.9мс / 3.0мс / 11.6мс |

\* артефакт первого прогона (CPU под нагрузкой); на повторных и 10k — 11.6 мс.

- На «честных» простых вопросах (L1–L4) все три варианта дают ~100% — разницы не видно.
- FTS5 впереди по Hit@10 потому, что в сгенерированных вопросах **есть точные имена** из документов.
- RAG стабильно лучший по **MRR и Overlap@5** (релевантнее ранжирует, а не просто «находит в топ-10»).
- Все три ломаются по-разному на агрегации (L5): file — 47–53%, fts держит 90%, rag 83–88%.
- 454 мс p95 на 1k — урок: **мерить нужно в чистом состоянии системы**, иначе CPU-перегрузка
  ложится на RAG (эмбеддинг запроса на CPU).

## Честные ограничения

- Реальные датасеты — **английские** (bge-m3 мультиязычный, RU-корпус не проверялся).
- Часть данных синтетическая (LLM-генерация, seed=42) — на ней fts≈rag по Hit@10,
  т.к. запросы содержат точные токены; реальные данные дали честную картину.
- Только retrieval-этап (LLM-judge и end-to-end ещё не прогонялись).
- Один корпус = одна доменная структура; «66k чанков» здесь — вики-параграфы,
  не обязательно 66k произвольных документов.
- Hybrid (вектор + BM25 + rerank) не сравнивался — вероятный следующий кандидат.

## Что внутри

```
harness/
  bench.py            # весь стенд: gen-corpus / gen-queries / index / search / judge
  report.py           # агрегация metrics.json -> summary.csv + report.md
  pipeline*.sh        # сквозные прогоны (1k / 10k / реальные датасеты)
  real/download.py    # скачивание MultiHop-RAG / RGB / HotpotQA
  real/convert.py     # конвертация датасетов в единый формат (chunks + queries + gold)
corpus/
  chunks_*.jsonl      # корпуса: 1k/10k (синтетика) + real-mh / real-rag-10k / real-rag-66k
  world_*.json        # «миры» синтетики (100/1000 сущностей)
queries/
  queries*.jsonl      # запросы с gold chunk ids и уровнями сложности
results/
  summary.csv         # все метрики (variant, scale, metric, value)
  report.md           # сводные таблицы
  {variant}_{scale}/  # metrics.json + search_results.jsonl (по запросу: топ-10 + gold)
images/               # графики (make_charts.py перестраивает из summary.csv)
```

## Как повторить

Зависимости: Qdrant (:6333), bge-m3 через llama-server (:8002, флаг `-ub 1024` обязателен),
Python 3.11+ с `requests` и `rank_bm25`. Форматы датасетов описаны в `harness/real/convert.py`.

```bash
# реальные датасеты (одноразово): скачать и сконвертировать
python3 harness/real/download.py && python3 harness/real/convert.py

# индексация и поиск: каждый вариант x каждая шкала
python3 harness/bench.py index  --variant {file,fts,rag} --scale {1k,10k,real-mh,real-rag-10k,real-rag-66k}
python3 harness/bench.py search --variant {file,fts,rag} --scale {...}
python3 harness/report.py        # -> results/summary.csv, report.md
python3 make_charts.py           # -> images/*.png
```

Стенд прогонялся на: Ryzen AI MAX 395 (32 CPU), 32 ГБ RAM, все модели локальные.
